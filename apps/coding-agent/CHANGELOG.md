# Changelog

## [Unreleased]

### Changed

- A message an extension's `message_end` handler returns is a new object instead of being copied into the finalized message. The agent applies it before notifying anyone, so every `message_end` listener, `session.messages`, the saved session, and the next request get the replacement. The message object passed to `message_start` handlers and to `message_end` handlers that ran before the one that replaced it keeps its original content; read the final message from `message_end` in session events, `turn_end`, or `agent_end`. The chat in interactive mode redraws a custom message an extension replaced at `message_end` ([docs](docs/extensions.md#events-and-concurrency))
- The error class `CredentialSynchronizationError`, whose type `index.types` exports, is a `Schema.TaggedError` class. `new` takes one `{...}` object of its fields; the old positional arguments moved to the static `create(...)`, and `make({...})` builds one from the fields. `_tag`, `message` and the fields keep their names and values
- Constructing one of these errors checks its fields against the schema and throws when one does not match
- Encoding one of these errors to JSON lists its keys in the schema's order and drops keys the schema does not declare

## [0.0.7] - 2026-10-28

### Added

- `search_sessions` searches the conversations and work of past sessions and every orchestrator thread: user messages, assistant text, tool calls with their arguments, and whole tool results however long. All words of a query must appear in one message part; Japanese, Chinese, and Korean words match anywhere inside longer text, and quoted words stay together. Results can be narrowed by kind, tool, role (`orchestrator`, `worker`, `reviewer`, `triage`, `advisor`, or an ordinary `session`), task, thread, round, working directory, and time, and name the session, its role, task, round, and thread, the entry, and a passage around the match; `action: "read"` continues reading the session from that entry, page by page. It is a default tool, read-only, so it also stays in `/ask`, and `/search [words]` opens the same search in interactive mode. The session files stay the record: the index under `<agent dir>/session-index/v<format>/` only points into them, and each msa uses the directory of its own format, so going back to an earlier msa keeps searching; each search first indexes what was appended since the last one, rereads rewritten files, and drops deleted ones of the session directories it searches; a result from a session directory it does not search is checked first, so deleted or rewritten files do not show. Updates from several processes at once are applied only to the state they were read from, so a search finds what was appended before it. A rebuild, when the index cannot be opened, records another format, fails to update or read, or stays locked for 10 seconds, writes a new file and switches to it once complete, so searches in other processes keep answering from the file they have open, appends included, without waiting; waiting for a lock does not hold up the rest of msa. A session file that cannot be read into parts is skipped and listed with the reason under the results until it changes ([docs](docs/session-search.md))

### Fixed

- Triage and advisor threads get `search_sessions` beside `read`, `grep`, `find`, and `ls`, and the triage, advisor, reviewer, and round review prompts tell them to look up the user's earlier instructions and decisions with it, narrowed to the task, round, or role ([docs](docs/session-search.md))
- `msa --help` and `msa --list-models` no longer start the orchestrator, so they no longer open `orchestrator.db` or migrate it.

## [0.0.6] - 2026-10-27

### Added

- Built-in tools can ask a classifier for a decision with `decide({ name, state, questions })`. The classifier is `decision.model`, by default `local/liquid-d1-3b`, Liquid D1 run in process through `node-llama-cpp`; each question carries its own threshold, which `decision.thresholds` overrides. msa starts fetching the classifier `decision.model` is set to into `<agent dir>/models` and loading it when it starts in interactive or RPC mode, and shows a warning if that fails; until the model is fetched and loaded a decision is `undecided` at once, and the next decision after a failure fetches it again. Offline, no path downloads it: msa uses only a model file already on disk, and decisions stay `undecided` without one ([docs](docs/settings.md))
- A task can carry checks: commands with the exit code, and optionally the output, they must give. `create_task`, `replan`, and `set_task_state` take them. When the worker ends its turn, the harness runs them in the worker's working directory before the reviewer starts and sends failing results back to the worker until they pass, however many turns that takes; only a turn that ends with exactly the same results as the turn before and leaves the worker's files as they were, committed or not, puts the task in `needs-decision`. `orchestrator.db` moves to schema 2, so an older msa stops with "Update msa" instead of running tasks without their checks ([docs](docs/cli.md#tools))
- In a git repository each work task runs in its own worktree and branch, which the harness creates next to the main checkout before the first thread of the task starts; the worker, its reviewer, a rerun, and the goal's checks all use it, and it stays when the thread ends. `create_task` and `replan` take `mergeInto`, another work task that has not started, whose branch this task branches from and merges into instead of opening its own pull request; a task's branch is cut after fetching the default branch from `origin`, and a `replan` task that would inherit a started target is refused; the harness makes that task depend on it, so `create_task` accepts a task with `mergeInto` and no `dependsOn` even when 3 or more tasks are unfinished. `orchestrator.db` moves to schema 3, so an older msa stops with "Update msa" instead of running every task in the main checkout ([docs](docs/cli.md#tools))
- The harness judges each task review with `decide`: when the reviewer ends its turn, the decision model reads the report and the task's goal state and answers whether a finding within the goal remains; it waits up to 10 minutes for the decision model to be fetched and loaded, so reviews are judged in print mode too. `pass` completes the task, `fail` sends the report back to the worker and reviews the fix again, however many rounds that takes, and `undecided` (no model, or no answer above the threshold) never completes the task: it goes to a triage like a decision request (see below), which continues the reviewer with its decision or puts the task in `needs-decision` and tells the orchestrator why. The verdict and its reason head the reviewer's report in `/tasks`. Each task report the orchestrator gets starts with the task's result (`completed`, `sent-back`, `waiting`, `stopped`, or `failed`) and carries it as its `status`, so the watchdog's stopped tasks and the recovery notice for tasks back to `waiting` no longer report `failed`. The verdict is stored with the report, so a worker that restarts after the session reopens still gets the findings and the next review is compared with them; `orchestrator.db` moves to schema 4, so an older msa stops with "Update msa" instead of completing reviewed tasks without a verdict ([docs](docs/cli.md#tools))
- In a repository with an `origin` remote, each work task carries its own pull request, which the harness finds from the task's branch and shows with its number, state, head SHA, CI result, and mergeable state in `list_tasks`, `read_task`, and `/tasks`. When the worker ends its turn, a default goal check sends the work back until that pull request exists, is pushed, does not conflict, is not behind its base, and is green on CI; while CI is only still running, or no check has registered on a new head yet, the harness waits for it without waking the worker, handing the stall to a triage after 3 hours (see below), which can continue the worker with a decision such as re-running CI, and a pull request whose head has had no check for 2 minutes passes as a repository without CI. When `gh` is missing, not logged in, or finds no GitHub repository at `origin`, the task stops with gh's reason. The reviewer gets the pull request's number and body to check against the final diff. After the review passes, the harness reads the pull request again, merges only when its head, title, and body are the ones that were checked and reviewed, squash-merges it at that head with that title and the pull request's commit messages as the commit message through GitHub's merge API, and completes the task only once the merge commit on GitHub is shown to be its own, then removes the task's worktree and branches locally and on `origin`. When CI is running again at that point, the harness waits for it before merging instead of waking the worker; a pull request that cannot merge goes back to the worker instead of completing the task, as many times as it falls behind its base, and when it cannot merge again at the head it was already sent back with, the task goes to `needs-decision` instead of going back again. When GitHub refuses the merge or the request ends without GitHub's answer, the harness reads the pull request again: merged is judged as below, behind goes back to the worker, and anything else stops the task with the reason. Workers and reviewers are told early when they try to merge or turn on auto-merge: on macOS and Linux their shell finds a `gh` wrapper first on `PATH` that refuses `gh pr merge`, the REST and GraphQL merge calls in `gh api` (also from a query file or stdin), and aliases that merge, and the GitHub MCP merge tools are refused; each refusal says why. The wrapper is an early warning, not the guard: a call that gets past it is caught afterwards from the harness's own record. Before each merge request, the harness records the head it merges and a random nonce that the request's squash message carries as an `Msa-Merge: <nonce>` trailer, then the merge commit GitHub returns when it accepts the merge, and clears the head and nonce when GitHub refuses it or its goal check or merge step reads the pull request as not merged (reading a task with `read_task` or `/tasks` leaves them). A merged pull request completes the task when its merge commit is the one GitHub returned, or, when the request got no answer or msa ended before it arrived, when the merge commit's message carries the recorded nonce, including after a session that crashed mid-merge reopens; any other merge, even at the same head right after GitHub refused the harness, makes the task `stopped`, not `completed`, and its report gives the merge commit, when it was merged, the account GitHub recorded (which can be the harness's own account), and the part of the harness's record that shows the merge is not its own; a merge commit whose message cannot be read stops the task without judging it someone else's, and a rerun judges it again; a pull request with auto-merge turned on stops the task at the goal check or before the harness merges, and the report names who turned it on. When GitHub accepts the merge but the pull request cannot be read back, the task still completes and cleans up. The worker ends its turn once the pull request is open and pushed; the harness waits for CI. A `replan` that replaces a task hands its open pull request to the new task, which continues on the same branch; a dropped task that still carries an open pull request is named in the replan result, and every report of a task that ends `stopped` or `failed` while carrying an open pull request, whether stopped from `/tasks` or `stop_task`, by the watchdog or by gh being unavailable, names that pull request and its branch. The pull requests live in a new table of `orchestrator.db`, which stays at schema 4, so msa 0.0.5 still opens the same database ([docs](docs/cli.md#tools))
- An orchestrator task can end waiting for a decision instead of passing or failing. Workers and reviewers get the `request_decision` tool, which records what of the goal cannot be met or contradicts itself, the options with their tradeoffs, and a recommendation, and ends the turn; the harness also asks for a decision when a review repeats the previous review's findings unfixed while the worktree holds the same files as at that review, when a turn ends with exactly the same goal-check results as the turn before, when the merge is blocked again at the head the work was already sent back with, when a resumed thread stops on the same provider error without progress, when CI does not finish, and when the review cannot be judged. Before the task waits, a read-only triage thread (its own detached checkout and only read tools plus `conclude_triage`) reads the goal, the request, the earlier triage decisions of the task (each request, the way it decided, and whether any file changed since), the diff, the pull request body, `AGENTS.md`, the commit log, the issues, and related tasks' reports, and looks for a way that meets every constraint: when it decides, the thread that stopped continues in its own session with the decision and its grounds, the task never waits, and the orchestrator gets the decision as a report; only billing, personal data, revoking an existing key, an unmade choice of specification, a compromise, or a request the triage finds to repeat one an earlier triage decided make the task `needs-decision`, and the report of a repeat carries the request beside the repeated decision's request and way so the orchestrator can answer one that is not a repeat with `send_message`; only the same request word for word skips the triage, so a different request, such as an undecided review after a triage had CI re-run, is triaged even when no file changed since the earlier decision. The task becomes `needs-decision`: it is not reviewed, completed, or merged, its dependents and its round's closing review keep waiting, it shows as `needs-decision` in `list_tasks`, `read_task`, and `/tasks`, and the orchestrator gets the request as a report. `send_message` answers it: the thread that stopped (the reviewer when the reviewer asked or the review could not be judged, otherwise the worker) continues from where it stopped with the request and the answer. `consult_advisor` (`a` in `/tasks`) starts an independent advisor thread that reads the task, the request, the reports, and the code, weighs the options, and returns its recommendation as a report while the task keeps waiting; the advisor has only read tools and runs in a detached checkout of the worker's current files, and is stopped when `send_message` answers the decision first. The checkouts of advisors and triages are removed with their git worktree entries when they end, when the session closes, and, for one a crash cut off, when the session reopens. A decision request whose triage the session closed or crashed in the middle of stays in `orchestrator.db`, and the reopened session triages it again before it starts other work, so the request is not lost and the task does not start over. The harness no longer fails or stops a task after a number of rounds: failing reviews, failing goal checks, and pull requests that fall behind or conflict at the merge go back to the worker until the goal is met. The decision model also answers whether every item of the goal is met, reading the report and the pull request body, and the review passes only when it is, so a report or a pull request that leaves a goal item as a known limitation, out of scope, or for later goes back to the worker. Reviewers record each goal item as met or unmet with `record_goal_items`; the goal state splits into items so that every requirement lands in one: each top-level list entry (`-`, `*`, `・`, `1.`, `1)`) with its nested lines, each numbered part (`(1)`, `①`) of a line or paragraph, and each sentence of the text around them, with code blocks kept whole; and the harness passes a review only when every item is recorded met, whatever the report or the decision model says; the last review's files live in a new table of `orchestrator.db`, which stays at schema 4 ([docs](docs/cli.md#tools))
- The orchestrator gets `merge_pull_request`, which squash-merges a pull request the way the harness merges a task's: only at the head it names, only while the pull request is open, current with its base, free of conflicts and auto-merge, and green in CI, with the message the harness builds, and it judges the merge its own the same way. A task's pull request merges only while the task is `stopped`, `failed`, or `completed`; the task then completes and its worktree and branches are removed, and a running task's pull request is left to the harness. The merge waits for, and holds off, the other orchestrator actions that change tasks, such as `rerun_task` and `stop_task`; the harness's own merge after a passed review does the same, and a merge that a stop interrupted no longer completes or cleans up a task that was rerun meanwhile. `msa squash-message <number> <head>` prints the message the harness and `merge_pull_request` send at that head, so CI can lint it before the merge ([docs](docs/cli.md#squash-message))

### Changed

- Long-term memory lives in [sepiace](https://sepiace.io) instead of `memory.db` and an embedding endpoint. msa adds sepiace as the built-in MCP server `sepiace`, signed in with `/mcp login sepiace` or `msa mcp login sepiace`. The `memory` tool takes one natural-language `request` that sepiace remembers, recalls, or forgets; every user prompt asks sepiace a question about what it remembers that is relevant to the prompt in the current repository, with the prompt only quoted and sepiace asked not to change memories (sepiace documents no read-only request, so whether it complies is up to sepiace), and adds the reply as the hidden `<memory>` block, giving up after 5 seconds. Memories belong to the sepiace account instead of a project or global scope. The `/memory` view shows the sepiace connection, whether recall runs, and whether `memory.db` still waits to move; `enter` sends a request typed into it and `r` turns recall on or off. `/memory <request>` sends a request directly. Listing, searching, adding, and forgetting memories by ID are gone, because sepiace returns no IDs. Requests that secretlint's recommended rules flag as holding a secret are not sent, and nothing is queued while sepiace is unreachable. The settings `memory.database`, `memory.embedding.*`, `memory.recall.limit`, and `memory.recall.minScore` are removed, and a settings file that still holds one gets a startup warning naming each key; `memory.database` is read only to move `memory.db`. After `/mcp logout sepiace` or turning the server off, the `memory` tool is removed and `/memory` shows sepiace as not connected. Extensions can remove a tool they registered with `msa.unregisterTool(name)`. The first prompt signed in to sepiace sends the memories in `memory.db` to sepiace, leaving out those that look like secrets, and renames the file to `memory.db.migrated` ([docs](docs/memory.md))
- MCP sign-ins are no longer written to `mcp-auth.json`. msa keeps them with the `credentialHelper` set in the global `mcp.json`, a program that speaks the Docker credential helper protocol, or else in the macOS login keychain or the Linux Secret Service keyring; when none works, such as over SSH on macOS, they last until msa exits: msa warns the moment it falls back to memory, at startup, on a token refresh, or at sign-in, in the session or on standard error in `msa -p` and JSON mode, with how to set `credentialHelper` and the servers whose sign-ins came from `mcp-auth.json`, and `msa mcp list` and `/memory` say that sign-ins are not saved. An existing `mcp-auth.json` moves into the store and is deleted after msa reads the tokens back from it; when only memory can hold them it is deleted anyway, so no token stays in a plain file, and the warning says so ([docs](docs/mcp.md#store-sign-ins))
- Every session's system prompt has a `development_style` section with msa's own way of working: choose the fix that removes the cause instead of asking the user to pick, fix every place with the same problem and add a guard against it coming back, keep reasons in commit messages, finish verification and cleanup without asking, search for recent facts and existing solutions, write lasting rules into the repository, rebase onto the branch it merges into before pushing, report the resulting state in a few lines with measured numbers and name a decision only when one is needed, and keep names untranslated. `--system-prompt` and `SYSTEM.md` keep it, and the orchestrator's reviewers judge work against it ([docs](docs/how-msa-works.md#context))
- `create_task` rejects a task without dependencies once 3 or more work tasks of the project are waiting or running; the error lists them and says to name a dependency or insert the task with `replan`. With 2 or fewer, `dependsOn` can still be empty. The orchestrator's tool guidelines now ask for strict dependencies: work on the same area, branch, or precondition is chained, parallel only when neither task depends on the other's result, and a red main gets one fixing task that the other work tasks wait for ([docs](docs/cli.md#tools))
- The orchestrator's task reviewer and each round's closing review fail the work on any finding within the task's goal, whatever its severity, and report findings within the goal, problems outside it, and what they checked under separate headings. Such findings are fixed in the same pull request and the work merges only after the review passes; only problems outside the goal become separate issues ([docs](docs/cli.md#tools))

### Fixed

- An orchestrator replan no longer leaves the tasks it replaces or drops `stopped`, where `keep`, `send_message`, or `rerun_task` could start them again next to their successors and the tasks behind them waited forever. They become `closed`: they never run again, `replan`, `send_message`, and `rerun_task` refuse them, and no task may depend on them. Tasks that depended on a replaced task depend on its successors, tasks behind a dropped task depend on what it depended on, and the replan result lists them under `rewired`. `create_task` and `replan` refuse a task with the title of an unfinished work task (`failed` included, since `rerun_task` resumes it) and name it, comparing titles as written apart from whitespace, and `create_task` refuses a `condition` that `/bin/sh -n` cannot parse instead of creating a task that never starts. `orchestrator.db` stays at schema 4, so an msa that knows schema 4 still opens it; a closed task stays closed whatever status that msa writes, and on opening, every task a recorded replan replaced or dropped is closed whatever status an earlier msa left or reran it to, `running` included, its threads stop, and what waited on it moves on; a run that ends after its task was closed leaves the task closed ([docs](docs/cli.md#tools))
- `pr_watch` counts a cancelled check that did not run again on the same head as cancelled instead of failed, and reports `CI finished: 2 passed, 1 cancelled. Run the cancelled checks again or push.`; a cancelled run that ran again is still left out, and a rerun that failed still counts as failed. An orchestrator work task whose pull request has such a check goes back to the worker to run it again instead of being told to fix a failure ([docs](docs/pr-watch.md))
- The orchestrator's squash merge no longer uses the pull request body as the commit body. It keeps the reviewed title as the subject and builds the body from the pull request's commits, which commitlint already checked, so tables and long lines in a pull request body no longer break `body-max-line-length` on `main`. It does not merge when GitHub lists the pull request's commits up to another head than the one it checked ([docs](docs/cli.md#tools))
- `msa --help` no longer lists `ANTHROPIC_OAUTH_TOKEN`, which no provider reads; Anthropic takes `ANTHROPIC_AUTH_TOKEN` as a bearer token and `ANTHROPIC_API_KEY` as the API key
- A worker or reviewer that ends on a provider error retries do not fix no longer fails its task. A Claude Code session limit, a 402, or any error the session's own model fallback treats as unusable puts the task back in `waiting`; `/tasks` and the session's report show the error and when it resumes. One minute after the reset time the error carries, or 15 minutes later without one, the same thread's session is reopened and told to continue. A resumed thread that stops on the same kind of error again before making any progress is not resumed again and not failed: like the other stops for work that is not moving, it goes to a triage, which continues the same session with its decision or puts the task in `needs-decision`, where `send_message` continues the same session; a wait an earlier msa left without a resume time moves to `needs-decision` when `orchestrator.db` opens. An advisor or a triage stopped by such an error waits for the reset without changing the task, so a task waiting for a decision stays `needs-decision` and no new worker starts before the answer; only that advisor or triage resumes, in its own session. `claude-subs` now marks a usage limit with the quota error kind and records the reset time on the error, so a session's own model fallback also moves past a Claude Code usage limit. Other failures stay `failed` and are not restarted ([docs](docs/cli.md#tools))
- `createAgentSession({ agentDir })` keeps `orchestrator.db` and `handoffs/` in that directory even when the settings manager is `SettingsManager.inMemory()` or comes from custom storage; they used to fall back to `MSA_CODING_AGENT_DIR` or `~/.msa/agent`. `AgentSessionConfig` takes the required `agentDir`, and `settingsManager.session.getOrchestratorDatabasePath` and `settingsManager.session.getHandoffDirectory` take it as an argument
- A task no longer stays `running` after its thread dies. The orchestrator checks its threads every minute and stops the ones with no tool call or message for 30 minutes (60 minutes while any tool call it made has not returned, including the rest of a parallel batch), the ones whose last turn ended in an error or abort without finishing, and the ones with no live run; a thread that is compacting is not checked. Their tasks become `stopped` or `failed`, and the session gets a report with the elapsed time. Tasks of another session whose orchestrator process is gone go back to `waiting`, as do a session's own running tasks when it closes or reopens; the reopened session gets a report with how long each had gone without an update. A report for a failed thread now says how long it ran ([docs](docs/cli.md#tools))
- A thread that completes, fails, or is stopped stops every pull request it registered with `pr_watch`, so a CI or review change no longer wakes a finished thread to push or merge
- `pr_watch` no longer reports a check as failed when its run was cancelled because the same check started again on the head, as when editing the pull request restarts its workflow; the orchestrator's pull request check reads CI the same way ([docs](docs/pr-watch.md))
- `/tasks` now lists the tasks of a round that a replan created; rounds missing from an existing database are added when it opens
- A model call that fails with 401, 402, 403, or a provider error naming a rejected key, an empty credit balance, or a spent quota is no longer retried. The session switches to the next model in `enabledModels` whose provider has not failed and resends the request; with none left it stops, writes the time and the error into the transcript, rings the terminal bell with an OSC 9 and OSC 777 notification (wrapped for tmux passthrough inside tmux), shows "(stopped)" in the terminal title, reports program status `blocked` with kind `auth` for a rejected credential or `quota` for a spent balance, and runs the new `notifyCommand` setting with the message in `MSA_NOTIFY_MESSAGE`. Switching the model resumes the run with the reports that arrived meanwhile ([docs](docs/settings.md#network-and-retries))

## [0.0.5] - 2026-10-20

### Added

- `/handoff [path]` writes the orchestrator's state to one Markdown file under `<agent dir>/handoffs/` and prints the line to paste into the next session. The tool fills in the tasks, notes, replans, running and waiting threads, and open PRs and issues; the model writes the premise, the goals in dependency order, and what not to start. A fresh interactive session asks once whether to resume from a handoff it has not offered before ([docs](docs/slash-commands.md#hand-over-to-the-next-session))

### Changed

- What the orchestrator runs for a task is a thread, so a session is only a saved conversation: `set_max_concurrent_sessions` is `set_max_concurrent_threads`, `/sessions` is `/threads`, `orchestrator.maxConcurrentSessions` is `orchestrator.maxConcurrentThreads`, `app.orchestrator.sessions` is `app.orchestrator.threads`, and the `msa.session` span, its `msa.session.*` attributes, and `msa_orchestrator_sessions_active` are `msa.thread`, `msa.thread.*`, and `msa_orchestrator_threads_active`. An existing `orchestrator.db` moves its `sessions` table to `threads` on open ([docs](docs/cli.md#tools))

### Fixed

- msa starts again after 0.0.4 opened an `orchestrator.db` that a newer msa had already moved to `threads`: the empty `sessions` table 0.0.4 left behind is merged into `threads` and dropped. `orchestrator.db` now records its schema version, and an msa older than the database stops with "Update msa" instead of changing it

## [0.0.4] - 2026-10-19

### Added

- The orchestrator tools are part of every session's default tools: the session breaks a request into tasks, each declaring its current state, the goal state, and its dependencies, and the scheduler starts tasks whose dependencies are finished within the concurrency limit and puts a separate reviewer session after each worker ([docs](docs/cli.md#tools))
- `set_task_depends` and `set_task_state` change a task's dependencies and its current and goal states before it starts; `/tasks` edits them with `d`, `w`, and `g` ([docs](docs/cli.md#tools))
- `replan` stops the running work at a turn boundary with a wrap-up (commit, push, handoff note), rewrites the DAG in one transaction, and resumes from the handoff ([docs](docs/cli.md#tools))
- `/sessions` starts a session and gives it instructions; a session can also be started after another one with `dependsOn`
- In fullscreen mode the screen splits into the conversation and a sessions pane; `Shift+→` opens `/tasks`, `Shift+←` or `Esc` returns, and dragging the divider or `Ctrl+Shift+←/→` resizes it ([docs](docs/cli.md#tools))
- `modelPolicy` hides models by pattern and keeps them in the picker under `hidden` with the pattern that hides each one; `/model upgrade` and the `model_upgrade` tool move the settings to a newer model ([docs](docs/models.md#restrict-models))
- `pr_watch` follows pull requests and tells the session when checks, reviews, comments, the base branch, or the merge state change; it is enabled by default ([docs](docs/pr-watch.md))
- msa sends traces, metrics, and logs over OpenTelemetry to `MSA_OTLP_ENDPOINT`, `telemetry.otlpEndpoint`, or a local `msa-grafana-lgtm` container it runs with podman; the Grafana URL is shown at startup and in `/status` ([docs](docs/telemetry.md))
- `/status` (`/context`) breaks the next request down into system prompt sections, each tool definition, conversation, tool results by tool, and compaction, with tokens and shares; RPC `get_state` carries it as `contextUsage`
- Pressing Enter three times in a row on an empty input sends every queued steering and follow-up message at the next turn boundary, in the order they were entered ([docs](docs/keybindings.md))
- OpenRouter requests send `provider.data_collection: "deny"` by default; set `compat.openRouterRouting.data_collection` to `"allow"` on a model to opt in ([docs](docs/providers.md#openrouter))
- `/ask <question>` runs a turn in which the model can only answer: only tools marked `readOnlyHint` are declared (`memory`, `pr_watch`, `model_policy`, and `model_upgrade` keep their read actions), the system prompt says to answer without starting work, and the next turn is back to every tool. RPC `prompt` takes `"mode": "ask"` and the SDK `prompt(text, { mode: "ask" })` ([docs](docs/slash-commands.md#ask-a-question))

### Changed

- The `anthropic` provider is now `anthropic-api` and `claude-code` is now `claude-subs`, so the pay-per-token API and Claude subscriptions read apart; credentials, `models.json` and settings move to the new ids on startup
- `claude-subs` and `opencode-free` are part of msa instead of built-in extensions, so `--no-extensions` keeps them; they are listed only when `claude` / `opencode` is installed
- `anthropic-api` takes API keys only: the Claude Pro/Max sign-in, `ANTHROPIC_OAUTH_TOKEN`, and the requests that posed as Claude Code are gone; a stored Claude Pro/Max sign-in is dropped on startup. Use `claude-subs` for a subscription
- `/accounts claude add|remove` rebuilds the `claude-subs-<account>` providers without reloading the session
- `claude-subs` lists versioned model ids only (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`, `claude-fable-5-1`); `opus`, `sonnet`, `haiku`, and `fable` are no longer accepted
- The orchestrator keeps tasks, sessions, reports, and shared notes in SQLite (`orchestrator.database`, default `<agent dir>/orchestrator.db`) instead of Neo4j; existing task prompts move to the current state on startup
- `create_task` and `replan` take `currentState` and `goalState` instead of a free-form prompt, and tasks no longer carry `paths`, `repos`, or `priority`

### Removed

- `--orchestrator`, now the default; passing it is an error
- `undo_replan`; run `replan` again instead
- The `NEO4J_*` environment variables for the orchestrator
- Built-in providers other than `anthropic-api`, OpenRouter, OpenAI, `claude-subs`, and `opencode-free`, along with the API implementations only they used (Mistral Conversations, Azure OpenAI Responses, Google Vertex, Bedrock Converse, and the Radius protocol). Add any of them back as a compatible endpoint in `models.json` ([docs](docs/models.md#configure-a-compatible-endpoint))

### Fixed

- `/tasks` and `/memory` scroll when the list or the details do not fit, with `PageUp`/`PageDown` and `Ctrl+D`/`Ctrl+U`
- Memory recall and search no longer wait on the embedding endpoint while no memory is stored
- OpenRouter and opencode requests report msa rather than pi
- `/effort` completes model ids again
